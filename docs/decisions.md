# 已确认的架构决策

| 决策 | 结论 |
|---|---|
| 项目边界 | 与 daily-work / Hub 完全独立 |
| 部署 | 实验室主机 windows-wg（Windows 10 LTSC 2019）原生安装，不使用 Docker（2026-10-12 改定，原因见下） |
| 分析数据 | 临时保存，下载后按 TTL 清理，不建历史归档 |
| 业务数据 | Guide、细胞、物料持久化到 PostgreSQL |
| Guide 隔离 | 每个用户独立，按 owner_id 强制隔离 |
| 物料维护 | 管理员通过 xlsx/csv 增量导入；普通成员可申请已用完，管理员批准、恢复及直接标记；每周六服务器时间 03:00 从 OA 网页重新登录、导出并增量同步，已部署 |
| 物料定位 | 采购记录查询（买过什么、品牌货号、谁请购、是否到货），不是实物库存；保留全部部门，页面展示指定部门；按采购单编码＋物料编码增量匹配，保留本地使用状态 |
| 常用耗材库存 | 顶部独立选项卡「常用耗材」，实物库存（`consumable_stock` + 核对台账）与采购记录分表；类别由 `MATERIAL_STOCK_CATEGORIES_JSON` 配置；数量只由人工核对改变，未核对不当作 0；查询/历史所有登录用户可看，写操作仅管理员。2026-10-20 起类别改「大类/子类」两级（标签卡=大类）、状态改三态、停用安全库存（列保留）。2026-10-21 起改为固定规格槽位：库存记在槽位上，按采购单位整箱计不拆、0 即需采购；采购按规则建议归位，管理员确认后记住货号；第一次核对为基线，之后按「工作台确认入库 + 定期盘点」更新，消耗/月优先按盘点差计算。设计见 `consumable-stock.md`，选型见 `material-inventory-research.md` |
| agent 库存校对 | 成员/agent 提交「库存校对请求」（库存数量建议 + 待标记已用完的采购记录），管理员在「物料审批 → 库存校对」批准后事务内生效；agent 使用普通成员账号，MCP 不提供批准工具，提交后库存不变。接口见 `agent-mcp.md` |
| 细胞位置 | 只记到「架号 + 层号」，不记孔位；按单个液氮罐设计 |
| 细胞取用 | 直接修改管数，系统自动记录谁、何时、从几改到几；不单独做取用登记 |
| 细胞权限 | 登录用户都可录入和修改；删除仅管理员；存放人为文字字段，不关联账号 |
| 表格读取 | xlsx 用 exceljs；SheetJS 读 WPS 生成的登记表会错位读取文本，已弃用 |
| 登录 | 用户名 + 密码（bcrypt），会话 7 天存库，连续失败 5 次锁定 15 分钟；不开放自助注册 |
| 文件重命名 | 不做独立工具；作为 Sanger 分析的结果命名规则，上传后前端实时预览，预览逻辑与 R 端逐条对照测试 |
| 分析排队 | 全站一个先进先出队列，同一时间只运行一个分析任务（R 服务单进程）；前端显示前方任务数、预计等待与剩余时间 |
| 纳米孔取数源 | 以厂商的 `Bam/*.sort.bam` 为主源（坐标与 fasta/频率表一致、与频率表逐位点等价且不随派生文件损坏），频率表 CSV 降为交叉校验与兜底（无可用 BAM 时用），截断/空文件/与 BAM 计数不符记为数据瑕疵（结果表 `Data_Source` / `Data_Note` 两列）；raw fastq 暂不接入（需比对器，另行立项）；EditR_wang 同步取数逻辑，但对外 summary 列与 Hub 派发不变（跨仓，待定）；证据与实测见 `docs/nanopore-data-source.md`（2026-10-13） |
| 固定资产 | 只导入资产名称、规格型号、类别、数量、存放地点、使用部门、使用人；仅研发部；跳过 SheetN 旧表，按资产编号跨表去重 |
| 下拉控件 | 全站使用可输入筛选的下拉框；筛选做 NFKC 规范化（全半角统一）、忽略大小写与空格，多关键词空格分隔，中文按片段匹配（不支持拼音） |
| 历史细胞数据 | 导入时保留原文，可识别的自动转换，无法识别的标为「待核对」后在系统内修正，不要求导入前手工清洗 |
| 冰箱管理 | 冰箱 → 容器（盒子/框）→ 样品；只定位到容器，不记孔位、不设盒子规格；一条样品 = 一管；冰箱清单由管理员预设（2026-10-13） |
| 冰箱权限 | 容器和样品归创建人，普通用户只看自己的；管理员有只读的全部人员视图，不能修改他人数据。只读查看全部冰箱内容的人员不设为管理员，而是普通成员加「冰箱总览」附加权限（账号管理中开关），无其他管理权限（2026-10-13） |
| 冰箱取用 | 批量取出只改状态、保留记录；批量转移到已有或当场新建的容器；流转历史写审计日志 |
| -80℃ 可视化 | 只给带架子的冰箱做布局图（目前 1 台 -80℃：4 层，每层 4 个架位；架子 5 层 × 每层 4 盒，规格可由管理员按实际调整）；-20℃、4℃ 为单层个人存放，保持列表。架子由管理员分配给个人，每人一个、不够再加；只有被分配的人能往里放盒子，别人只看到占用数。最下层放 2 个公共框，所有人可存入和查看，每管样品仍只有存放人能操作。盒子定位到「架内层 + 盒位」，不做盒内孔位（2026-10-13） |
| 冰箱选项卡 | 按台分（同温度有多台时分别显示），不再按温度分（2026-10-13） |
| 细胞冻存录入 | 细胞名称、来源、冻存液、存放人可从台账已有值中选，也可手填新值（不单独建字典表，保存后自动成为候选）；放入时间默认当天；只剩 1 管的记录高亮，取出最后一管需二次确认；可按勾选或筛选结果导出 Excel（2026-10-13） |
| 作图 | V1 不包含 |
| 推送/分享 | V1 不包含。留言板（成员只向管理员反馈、管理员回复）不属于推送/分享：不发通知，只在导航栏用角标提示未读（2026-10-13） |
| 外部系统 | V1 不对接 Hub、Grist、eLabFTW、webhook |
| 原始数据 | 不进入 Git，不进入生产数据库 |
| 分析失败原因 | 「厂商交付文件损坏/截断」与「目标位真的没有覆盖」分开记录，前者算数据瑕疵（要求重发），不写成「读不出」这类无法定位的原因 |

## 部署改定说明（2026-10-12）

原计划「Windows Server + Docker Compose」。核对服务器资料后：

- 同事电脑所在的单位网络里，只有 windows-wg 能直接访问；my-server、ubuntu-wg 等只在 WireGuard 内网。
- windows-wg 为 Windows 10 LTSC 2019（内部版本 17763），不支持 WSL2，无法运行 Docker Desktop；内存 8 GB，且已承载标签打印服务和 MariaDB。

因此改为在 windows-wg 上原生安装 Node.js、PostgreSQL 16、R，按开机自启服务运行。`infra/docker-compose.yml` 不再作为生产部署方式，仅可选用于开发机本地起数据库。资源约束：Nanopore 单任务大小和并发需设上限，临时工作区放在空间充足的 E: 盘。
