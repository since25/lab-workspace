# 纳米孔取数源：为什么主源应该是 BAM

2026-10-13 写，同日按复核结果修订并落地。起因：一个订单（下称 `ORDER_A`）的
`S-6` 管在跑分析时被判「目标位那一行读不出深度」。追下去发现两件事：一是厂商的
派生文件会坏，二是取数层把 BAM 这条最可靠的路放在一边没用。

本文记录证据（可复核）、原因分析、方案对比与落地情况。

> 数据边界：本文只用占位编号（`ORDER_A`、`S-n`），不写真实订单号、样品编号、
> guide 序列与本机路径。原始交付包只留在本机，不进仓库。

---

## 1. 现象

- 订单 `ORDER_A`：56 管，扩增子 555 bp，ABE（A→G）。
- `S-6` 在 R 引擎里出一行 `目标位那一行读不出深度`（`apps/r-engine/R/nanopore.R`
  的 `nano_analyse()`，`skipped_reason` 分支），`Depth` 为 `NA`。
- 同一批其余 55 管正常。

坐标：设计序列 20 nt，落在扩增子 225–244 位；目标位为设计序列第 7 位，即扩增子
**231** 位（+链，1-based）。反向交付样本中同一物理位点在 **325** 位（碱基身份 T→C）。

---

## 2. 证据（2026-10-13 两次独立复核）

### 2.1 直接原因：频率表被截断

| 样本 | 文件大小 | 完整数据行 | 是否盖住 231 位 |
|---|---|---|---|
| S-6 | 16384 B（4×4 KiB） | 156 + 半行 | 否 → 报错 |
| S-54 | 28672 B | 273 + 半行 | 是 |
| S-31 | 45056 B | 431 + 半行 | 是 |
| S-39 | 53248 B | 510 + 半行 | 是 |
| 正常样本 | 约 58 KB | 555 | 是 |

- 共同特征：大小是 4 KiB 整数倍、文件不以换行结尾、最后一行断在半行。
- 目标位 231 > 行数 → `nano_read_site()` 返回 `NULL` → 置 `skipped_reason`。
  引擎在这里停住是对的（读不出 ≠ 没编辑），错的是原因说不清。
- 另外三管「没报错但数据不全」：窗口外的逐位点表会缺。
- 旧代码会把那半行也当一行读进来（`fill = TRUE`），半行里的计数不可信。

### 2.2 不是本地下载/解压坏了

直接读压缩包条目：`S-6` 的频率表在 zip 里就是 16384 B，CRC 校验通过，
与磁盘文件逐字节相同 —— **厂商打包时文件就少了一块**。厂商 QC 报告里该管为
「本次成功」，即厂商自己没发现。

### 2.3 S-6 的真实数值

| 来源 | 深度 | 231 位碱基 | 编辑率 |
|---|---|---|---|
| `Suspious_sites/*.csv`（完整） | 391 | A 357 / G 33 / Del 1 / Ins 1 | 8.44% |
| `Bam/*.sort.bam` | 391 | A 357 / G 33 / Del 1 / Ins 1 | 8.44% |
| `fastq/*.fastq`（锚点法，205/431 条读） | 205 | A 182 / G 19 / C 4 | 9.27% |

判定：基本未编辑 / 混合群体（约 8%）；深度 391 < 1000，置信度低。

### 2.4 BAM 才是最完整的那一份

BAM 头显示厂商用 `minimap2 -ax map-ont --MD --secondary=no` 把这一簇的读比对回
**这管自己的一致性序列**（参考长 555）。由此：

- **坐标天然一致**：BAM 的 1-based 位置 = fasta / 频率表的行号。定窗口、镜像行号、
  翻碱基那三步一行不用改。
- **barcode/接头前缀已被软剪切**（CIGAR 多为 `18S555M18S`）。
- mapq 全 60；约 93% 的读覆盖全长。
- **逐位点计数与频率表 56/56 管逐格相等**（Depth、A/C/G/T、Del、Ins 全部，
  在频率表有数据的位置上）。复核时确定的计数口径：
  - `M/=/X` 记碱基，非 ACGT 碱基只进深度；`D/N` 记缺失；`S/H` 只推进读段；
  - **插入记在插入之后那一位**（记在之前那一位，每管有 10%–25% 的位点对不上）；
  - 深度 = A + C + G + T + 缺失，插入不进深度；
  - 跳过 `flag & 0x904`（未比对 / secondary / supplementary）。本单没有被跳过的记录。
- **截断不会跟着坏**：`S-6` 的频率表停在 156 行，BAM 照样给出 231 位
  A357/G33/Del1/Ins1，guide 窗口全长都在。
- 体积：BAM 中位约 105 KB/管，整单约 6 MB。
- `.bai` 是极简索引，不用；整份顺序读即可。
- BAM 只含该簇的读（本管 391/431 条 fastq 读），与厂商报的 `num` 同口径，
  但看不到次要簇。

### 2.5 raw fastq 做主源的代价（实测）

- `S-6`：431 条读，锚点法只定位成功 205 条（47.6%）。
- 朴素取碱基给出 9.27%，真值 8.44%（相对偏 +10%）。
- 要用 fastq 做主源，等于在系统里塞一个比对器或自己写 gapped 对齐，重做厂商已经做好的活。

---

## 3. 原因分析

1. **数据层（直接原因）**：厂商交付的派生文件 `Frequency_tables/*.csv` 在打包时被截断。
   历史上还出现过 0 字节空文件、`\t` 与 `,` 分隔符混用。它们是派生物，坏了不影响原始数据。
2. **设计层（我们的问题）**：取数层把唯一的取数路径押在这个派生文件上，派生物一坏就表现为
   「目标位读不出深度」——分不清「文件坏了」「真的没覆盖」「坐标算错了」。

一句话：**问题不在「CSV vs fastq」二选一，而在于「用派生物当唯一主源」。**

---

## 4. 方案对比

| | BAM 为主源（已采用） | CSV 为主源（原状） | fastq 为主源 |
|---|---|---|---|
| 坐标 | 现成，与 fasta/CSV 一致 | 现成 | 无，需自己对齐 |
| 交付可靠性 | 高 | 低（本单 4/56 截断） | 高 |
| 与厂商数字对数 | 直接 | 直接 | 不直接 |
| 依赖 | 纯 R 可解 | 无 | 比对器或自实现 |
| 体积（中位） | 约 105 KB | 约 56 KB | 约 651 KB |

结论：**主源用 BAM；CSV 降为校验与兜底；fastq 暂不接入**（原稿写「fastq 最后兜底」，
但 §2.5 已说明它需要比对器，作为兜底同样要先有比对器，不划算；需要时单独立项）。

## 5. 落地（2026-10-13 已实施）

### 5.1 取数顺序：BAM → 频率表

`apps/r-engine/R/nanopore.R`：

- `nano_read_bam()`：纯 R、零依赖。`gzfile()` 顺序读完 BGZF 的所有段，按上面的口径逐位点累计，
  返回与频率表同形的表，`nano_read_site()` 起往下的逻辑不动。
  - 注意：**不能用 `memDecompress(type = "gzip")`**，它只解第一段（实测 400 KB 的 BAM 只读出 1 KB）。
  - 参考不止一条、解析失败、或参考长度与一致性序列不符 → 不用 BAM，回退频率表，并在 `data_note` 里写明。
- `nano_read_table()`：文件不以换行结尾时丢掉最后那半行。
- `nano_frequency_defect()`：频率表为空、行数少于扩增子长度、或与 BAM 逐位点不符 → 记一条数据瑕疵
  （如「厂商交付的频率表疑似截断（只有 156 行 / 共 555 行）」）。用了 BAM 时，瑕疵不影响结果。
- 每个样本带 `source`（`BAM` / `频率表`）与 `data_note`；`nano_analyze_rows()` 返回 `sources`。

本单实测：56/56 管走 BAM、全部可读，4 管记「频率表疑似截断」；`S-6` 231 位为 8.44%；整单读包约 3 秒。

### 5.2 读不出的原因分开

| 情况 | `skipped_reason` | 归类 |
|---|---|---|
| 频率表为空且没有可用 BAM | 原文案「这个样本的频率表是空文件，读不出任何位点」不变（它进 EditR 推 Hub 的金样，改字属跨仓）；`data_note` 另记「厂商交付的频率表是空文件」 | 厂商文件 |
| 频率表截断到目标位之前且没有可用 BAM | 厂商交付的频率表被截断（只有 N 行 / 共 M 行）…（数据瑕疵，可要求厂商重发） | 厂商文件 |
| 目标位深度 0 | 目标位没有读段覆盖（深度 0） | 样本 |
| 一致性序列长度与这批不符 | 原文案不变 | 配置/坐标 |

### 5.3 各端的接入

- **lab-workspace**：上传时除三类文件外再解出 `Bam/*.bam`（`.bai`、fastq、QC 仍不落盘）；
  summary 末尾加 `Data_Source`、`Data_Note` 两列，页面与下载的 Excel 都可见。
- **EditR_wang**：`R/nanopore.R` 同步同一套取数逻辑；本地上传入口的浏览器拆包多带 `Bam/*.bam`。
  **没有**加 summary 列、没有升方法版本号、Hub 派发仍只送三类文件——那些会牵动 Hub，
  属于跨仓改动，需另行拍板（见该仓 progress 记录）。

### 5.4 回归用例

全部用合成数据（`apps/r-engine/tests/fixtures/nanopore_synth.R` 的 `write_bam()` 等），
真包不进仓库：`apps/r-engine/tests/test_nanopore_bam.R` 覆盖 BAM 计数口径（软剪切、插入、
缺失、N、secondary/supplementary）、BAM 与频率表一致、截断有 BAM / 无 BAM、计数不符、
BAM 损坏与长度不符的回退、深度 0。

## 6. 如何复核

全部为只读解析，可在本机对原始交付包复现：

- 文件截断：比对 zip 内条目的 `file_size` 与 CRC，检查文件末字节是否为换行。
- BAM/CSV 一致性：按 §2.4 的口径对每个样本累计逐位点计数，与频率表逐格比对。
- 引擎结果：`nano_read_package(<订单目录>)` 后看每个样本的 `source` / `data_note`。
